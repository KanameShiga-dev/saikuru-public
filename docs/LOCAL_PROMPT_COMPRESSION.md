# 計画時の圧縮とローカルでの要件保持の照合（2026-10-11）

## 方針

計画担当が作業指示を生成する段階で、同じ対象・条件・時点の重複説明を省く。
目的、全成果物、必須要件、禁止事項、数値、期限、保存先、受入条件、例外、根拠、未確認事項、承認範囲を保持する。
似ていても適用先が異なる説明は削らない。目安を合格条件に変えない。必要な制約は各担当の指示にも残す。
クラウドへの別の要約呼び出しは追加しない。

元の依頼は書き換えない。作業ボードには引き続き元の依頼と計画を渡す。
これは文脈予算や自動画像化とは別の処理である。画像化のしきい値・送信処理は今回変更していない。

## ローカルでの照合

- 作業ボード：計画担当が返した全作業のinstructionと、元の依頼＋今回の計画指示を照合する。
- 台帳相談：planモードの下書きと、送信対象に含めた利用者の相談文を照合する。通常の相談では呼び出さない。照合対象を末尾だけに切り捨てず、上限を超えた場合は未検査にする。
- 固定の数値・識別子チェックと、ローカルLLMによる目的・制約・否定・例外・時点・主体・許可の点検を組み合わせる。
- `equivalent`と4種の指摘配列を必須とするJSON Schemaで回答を制約する。形式不正・不明は合格にしない。
- 比較モード（shadow）。不一致で作業を自動停止しないし、圧縮案を実際の指示に自動適用しない。モデルの合格だけで意味保持を保証しない。
- 既定モデルは利用者の指定に従い、インストール済みの `gemma4:latest`（8.0B、Q4_K_M）へ変更。狭い構造化点検ではthinkingを無効にし、30秒の時間上限を維持する。Qwenへの自動フォールバックはしない。
- 固定の `http://127.0.0.1:11434/api/chat` のみ。Proxy・リダイレクト・外部モデル・自動ダウンロード・クラウドへの代替送信・ツール実行は行わない。
- 最大30秒、同時1件。利用不可・混雑・上限超過時も原文と通常の計画処理を維持する。キャンセルは呼び出し前後に確認する。通信中の中止反映は最大タイムアウトまで待つ場合がある。
- 原文＋計画の同一組み合わせは、プロセス内で最大32件・1時間だけ点検結果を再利用する。原文・圧縮案・モデルの指摘本文を追加でディスク保存しない。

## 設定と記録

`local_summary`の既定値：

```json
{"mode":"shadow","model":"gemma4:latest","min_chars":2400,"max_chars":16000,"timeout_seconds":30}
```

`mode`はoff/shadowのみ。`on`は未提供で、設定検証で拒否する。
`min_chars`は単独の圧縮案評価関数 `analyze` に適用する。短文を再要約せず原文を返す。
通常の計画処理では `analyze` は呼び出さず、`review_plan`による照合1回だけを行う。短い依頼でも禁止事項があり得るため、計画照合は文字数の下限で省かない。
`max_chars`は照合する原文＋計画の合計上限。途中を切り捨てて検査せず、上限超過は未検査として記録する。
ローカルのトークン窓での切り捨てを避けるため、送信メッセージのUTF-8バイト数にも保守的な上限を設ける。超過時は点検不能として原文を維持する。文字数だけで入力トークン数を保証しない。

計画担当のagent_run.local_summary、相談のcalls[].local_summaryに、モデル、判定状態、所要時間、ローカル入力・出力トークン、呼び出し数、再利用有無を記録する。
取得不能な消費はnull。クラウドのトークンにローカル消費を混ぜない。
計測出力 `team_optimization_metrics.py` にもローカル照合の列を追加した。
文字数差をクラウドの削減率や料金に換算しない。クラウド総消費・成果物品質・追加待ち時間を今後の実依頼で比較する。

## 検証と未確認

- 分離テスト：重複の扱い、必須条件・数値の欠落、不確実、形式不正、タイムアウト、結果再利用、原文維持を確認。
- 実Ollama：架空の営業ツール操作資料という自然な依頼で、正常／PowerPoint欠落／15分から10分への変更／禁止操作の許可への変更を照合。
- 1.5B初回は回答形式不正。JSON Schema導入後も正常例を誤判定した。証拠は保持。
- 7Bの4条件は期待と一致。約8.1〜19.8秒、合計ローカル入力2,515・出力205トークン。クラウド呼び出し0。
- モデル変更の追試：Gemma 3 4BはPowerPointの欠落を見逃した（4条件中3条件一致）。採用しない。
- Gemma 4の思考有効時は30秒上限を超えたため中断。thinking=falseで同じ4条件を再試験し、4条件すべて期待と一致。約14.3〜20.8秒、合計ローカル入力2,040・出力310トークン、クラウド呼び出し0。`data/local-summary-20261011/real-results-gemma4-no-thinking.json`参照。初回・失敗の証拠も保持。
- 既定をGemma 4へ変更後も26件の分離テスト通過。待機・稼働作業0件を確認して再起動し、稼働APIのlocal_summary.modelがgemma4:latestであることを確認。
- 少数例であり、一般的な意味保持・プロンプト注入耐性・複雑な依頼・成果物品質・実サービスの一巡・実際の削減効果は未確認。
- 26件の分離テストを通過。稼働・待機中の作業がないことを確認してサービスを再起動し、8790番のhealth HTTP200を確認。新しい計画から適用される。実サービスを通したAI依頼の一巡は未実施。

## 実依頼での追試と制限（2026-10-12）

開発・資料作成の36件を作業ボード経由で計測し、全件の成果物確認と受領まで実施した。
ただし各条件は少数回で、キャッシュを独立に制御していないため、観測した消費量の差を機能単独の削減効果と断定しない。
Gemmaによる計画照合は4件中、合格0件・不一致3件・タイムアウト1件だった。数値を文章中の文字一致で照合する処理には、計画構造に存在する工程数を欠落と扱う誤判定も確認した。
比較モードは自動停止や指示置換を行わない。常時有効化によるトークン削減は確認できておらず、設定のoffも選択肢とする。今回の公開で既定値や判定処理の追加改善は行っていない。
計測DB・依頼内容・生ログ・端末固有の証跡は公開物に含めない。上記の検証記録のパスは開発環境用であり、公開リポジトリに実データを配布するものではない。

## 復旧手順

照合だけを無効化する場合はlocal_summary.modeをoffにして再起動する。元の依頼・計画・DBスキーマは変えていないためデータ変換は不要。
計画時の簡潔化指示も戻す場合は、今回追加したCOMPACT_PLAN_GUIDEの呼び出しを戻す。
