# Claude Code のログインが切れる問題の修正（長期の鍵と、切れたときの待機・通知）

2026-10-12、利用者の承認による変更です。

## 現象
采来の Claude の担当が、数時間から半日ほどで「未ログイン、または認証期限切れ」になり、作業が止まりました（10-09 21:14、10-11 01:24・17:04）。
夜間に切れると、朝まで依頼が止まったままになります。

## 原因（見立て）
- 通常のログインは、利用の鍵（約8時間）と更新の鍵（約30日、使うたびに入れ替わる）の組です。
- 采来は複数の Claude の担当を同時に動かし、さらにログインの確認（`auth status`）を毎分と作業の前に行っていました。
- 利用の鍵が切れる瞬間に、複数の Claude Code が同時に更新しようとすると、後の方は入れ替わり済みの古い更新の鍵を使って失敗し、ログインが消えます。
  記録の「OAuth session expired and could not be refreshed」と、ログインから約8時間後に切れていた時刻が、この見立てと合います。

## 変更
### A：長期の鍵（`team_claude_auth.py`・`store_claude_token.py`）
- 利用者が `claude setup-token` で作った長期の鍵（有効期限は約1年、更新なし）を、Windows の資格情報の保管庫（汎用、名前 `saikuru/claude-oauth-token-local`、この PC だけ）に保存します。名前は 2026-10-15 に変えました（下の「2026-10-15 の追加の修正」）。
- 保存は `python store_claude_token.py` で行います。鍵は画面に表示されない入力欄に貼り付けます。2回続けて貼り付けた場合は保存しません。`--delete` で削除します。
- 采来は保管庫から鍵を読み、**Claude の担当として起動する CLI だけに** `CLAUDE_CODE_OAUTH_TOKEN` として渡します。Copilot など他の処理には渡しません。
  環境に `ANTHROPIC_API_KEY` があると鍵より優先されるため、その CLI の環境からは外します。
- 鍵があるときは、通常のログインの確認（`auth status`）を行いません。画面の表示は「長期の鍵でログイン済み」です。
- 鍵の値は、DB・イベント・ログ・画面のどこにも出しません。表示は「設定済みかどうか」だけです。
- 校正（`team_context_calibrate.py`）も同じ鍵を使います。
- 鍵がなければ、これまでどおり通常のログインを使います。

### C：ログインが切れたときの待機と通知（`team_engine.py`・`server.py`・`team_notifications.py`）
- Claude の担当が認証の誤りで止まったら、その作業を失敗にせず「待機」（`claude_auth_wait`）に戻し、ほかの Claude の作業も始めません。
- Windows の通知でお知らせします（PC通知がオンのとき。作業が止まるので業務時間外でも送ります）。切れたままなら2時間ごとに再通知します。
- 待機は、ログインし直してログイン情報のファイルが書き換わるか、保管庫の鍵が変わると解け、作業は自動で再開します。
  「ログイン済み」と表示されていても実際には使えない状態で、同じ失敗を繰り返さないためです。

## 確かめたこと（導入先PC）
- 長期の鍵だけで Claude Code が応答する（通常のログイン情報のない空のフォルダを指定して確認）。
- 采来を通した依頼（計画・実装・完了条件の確認・レビュー・セキュリティレビュー）が、長期の鍵ですべて成功し、受け入れまで進む。
- 担当が動かすコマンド（Bash）とフックからは `CLAUDE_CODE_OAUTH_TOKEN` が見えない（Claude Code が取り除いている）。采来の承認フックが使う `AGENT_TEAM_RUN_TOKEN` は見える。
- `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` は**使わない**：`AGENT_TEAM_RUN_TOKEN` も消え、采来の承認フックが動かなくなるため。
- 鍵を設定すると `claude auth status` は鍵が正しいかどうかに関係なく「ログイン済み」と答える（正しくない鍵でも同じ）。そのため采来は、この表示ではなく実際の呼び出しの結果で判断する。

## 確かめていないこと
- 実際にログインが切れたときの待機・通知・再開の一連の動き（単体テストでは確認済み、実機では未発生）。
- 1年後の鍵の期限切れ（期限が来たら作り直して `store_claude_token.py` で保存し直す）。

## 2026-10-15 の追加の修正
### 見つかったこと
- **長期の鍵は働いていなかった**：保管庫の `saikuru/claude-oauth-token` は 10-12 に `cmdkey` で空の値が書かれ、しかも「会社のネットワークで同期される形」（Persist = 3）でした。10-15 に `store_claude_token.py` でこの PC だけの形で保存し直しましたが、約30分後に同期で空の値に戻りました。そのため采来は通常のログインで動き続けていました。
- **利用上限の待機が明けると、ログインが消えた**：待機中に利用の鍵が切れ、再開時に複数の担当が同時に更新していました（10-11 19:03 は2つの担当が3秒差で失敗、10-15 10:38 はログイン情報のファイルが空の値で書き戻された）。毎分の `auth status` と、作業の前の `auth status` も更新のきっかけになりえます。
- **ログインし直したのに、すぐ待機に戻った（10-15 11:06）**：作業の割り当てが、毎分しか更新されない古い「未ログイン」を見ていたためです。

### 変更
- 保存先の名前を `saikuru/claude-oauth-token-local` に変え、この PC だけの形で保存する。`store_claude_token.py` は、保存後にこの PC だけの形で入ったかまで確かめる。古い名前は読まない。
- ログイン状態は、ログイン情報のファイル（`.claude-sairai\.credentials.json`）の鍵の有無と期限で判断し、`claude auth status` を起動しない（ファイルが読めないときだけ使う）。作業の割り当ては、毎回その時点の状態を読む。
- 長期の鍵がなく、利用の鍵の期限が10分以内（または切れている）ときは、Claude の担当を1つずつ起動する（承認待ちの担当は数えない）。
- 保管庫の鍵が空・形が正しくない、同期される形で保存されている、古い名前だけが残っている、保存から約11か月たった、のいずれかなら、画面と PC の通知で1回知らせる。

`test_claude_login_resilience.py`（ファイルによるログイン判定、待機の解除が古い状態で戻らないこと、更新が近いときに1つずつ起動すること、鍵の点検と知らせ、起動前の確認で `auth status` を使わないこと）。
