# モデル評価の計画（開発・資料作成）2026-10-09

## 目的
最新世代のモデルを実装担当にしたとき、**工程（動作の違い）**と**できばえ（コーディング能力・文書能力）**を同じ条件で測り、記録する。
エラーが起きても、すべての依頼を受け入れまで進める。エラーや利用者の介入は減点で記録する。

### 固定する担当（比べたいのは実装担当だけなので、ほかはそろえる）
- 計画：Copilot GPT-6 Sol（今日の試験で安定していた）
- レビュー（通常・セキュリティ）：Copilot Claude Opus 5.5（今日の試験で根拠が具体的だった）
- 注意：レビューが Claude 系なので、Claude 系の実装に甘くなる可能性がある。そのため、できばえは、レビューの判定ではなく、下の**隠しテスト**と**チェックリスト**で測る。

## 課題（全モデルに同じものを出す）

### 課題C：開発（既存コードの修正と機能追加）
- 用意する材料：小さな Python プロジェクト（家計簿のCSV集計）。既存テスト付き。**既知の不具合2件**（月の境界の扱い、全角数字の金額）と、**追加機能1件**（カテゴリ別の月次集計を CSV で出力）を依頼する。
- 測る力：既存コードを読む力、不具合の特定、既存の動作を壊さずに直す力、テストを書く力。
- 依頼文には、完了の条件として既存テストと追加テストのコマンドを書く。
- **隠しテスト**（担当には見せない、15件程度）を、受け入れのあとで私が実行して、合格率を測る。

### 課題D：資料作成（PowerPoint）
- 用意する材料：社内向けの架空の説明資料の元になる Markdown（約2,000字。数値・手順・注意事項を含む）。
- 依頼：新人向けの説明スライド（8〜10枚、表を1つ以上、図を1つ以上、発表者メモ付き）を、資料作成の依頼として出す。
- 測る力：要点の抽出・構成力・正確さ（元資料にない数値や事実を作らない）・表と図の使い方・日本語の自然さ。

合計：9モデル × 2課題 ＝ **18件**。

### 追加の課題（2026-10-09 追加。課題C・Dではほぼ全員が95〜100点になり、差が出なかったため）

#### 課題E：開発（難しめ。症状だけの不具合・複数ファイルの変更・あいまいな依頼）
- 材料：備品の貸出管理ツール `kashidashi`（`models.py`・`storage.py`・`service.py`・`cli.py` の4ファイルと既存テスト、本番の記録 `data/loans.csv`）。
- 不具合3件は、利用者の報告（症状）だけを伝え、原因の場所は書かない。原因はそれぞれ別のファイルにある（再貸出の判定＝service、古い日付の読み方＝storage、`--days` の型＝cli）。
- 部署の追加は、データ・保存・処理・コマンドの4ファイルにまたがる。部署の列がない古い記録を読めることも必要（依頼文には「本番の記録は書き換えない」とだけ書く）。
- 「延滞の一覧を部署ごとに分かりやすく」は形式を決めずに頼む。隠しテストは、どの解釈でも満たすべきこと（延滞分がすべて出る、返却済み・期限前は出ない、同じ部署がまとまる、部署なしの行も出る）だけを確かめる。
- できばえ（70点）：隠しテスト15件の合格率 40点、元のテストが合格 10点、追加テストが不具合3件と部署を確かめている 10点、README に `--dept` の説明 5点、`data/loans.csv` を書き換えていない 5点。

#### 課題F：資料作成（Word。長い資料の要約の正確さ・事実の誤り・構成）
- 材料：勤怠管理システム更改の検討経過報告（第1回〜第4回の会議記録・表5つ・他社事例・用語、空白を除き約4,400字）。途中で見直された数値（稼働時期の延期、見積の値下げ、対象人数の更新）と、採用されなかった意見をそのまま含む。
- 依頼：役員会向けの要約 `summary.docx`（1,500〜2,500字、冒頭に結論、見出し、比較の表、未決事項と今後の予定）。
- できばえ（70点）：要件 10点、要点12項目の網羅 15点、正確さ 25点（古い数値・誤った記述の「わな」9種類は1件ごとに −5、元資料にない数値は1件ごとに −3）、構成 10点（冒頭の結論・未決事項の見出し・段落の長さ）、日本語 10点。
- わなの例：稼働開始を「2027年4月」と書く（延期済み）、年間の利用料を「680万円」と書く（620万円に変更済み）、「A案が最も安い」と書く（5年総額はB案のほうが150万円安い）。「当初」「延期」など、変更の経緯として書いた場合は誤りにしない。

## 評価項目と配点（1件100点。エラーや介入は減点）

### A. 工程（30点）—— 采来の記録から自動で集計
| 項目 | 配点・減点 |
|---|---|
| 計画どおりの工程で進んだ（工程外の作業・範囲外の変更がない） | 10点 |
| 采来の確認を守った（拒否された操作・保護ファイルへの書き込みの試みがない） | 5点 |
| 実行結果の記録がそろっている（完了条件のコマンドを書かれた形で実行） | 5点 |
| 報告の正確さ（報告の内容と、実際の成果物・実行結果が一致） | 10点 |
| 減点：レビューの差し戻し | 1回につき −3 |
| 減点：利用者への質問（判断が必要な正当なものを除く） | 1回につき −3 |
| 減点：担当の失敗・エラー（報告の形の修正、時間切れ、CLIのエラーなど） | 1回につき −5 |
| 減点：自動修正の上限で停止 | −10 |
| 参考（点数に入れない）：所要時間、クレジット・トークン、道具の使用回数 | — |

### B. できばえ・開発（70点、課題C）
| 項目 | 配点 |
|---|---|
| 隠しテストの合格率 | 40点 × 合格率 |
| 既存テストが全部合格（既存の動作を壊していない） | 10点 |
| 追加したテストの質（不具合2件と追加機能をそれぞれ確かめている） | 10点 |
| 変更の小ささ・読みやすさ（不要な変更がない、関係ないファイルを変えていない） | 10点 |

### C. できばえ・資料（70点、課題D）
| 項目 | 配点 |
|---|---|
| 要件（枚数・表・図・発表者メモ）を満たす | 15点 |
| 正確さ（元資料にない数値・事実の作り話がない。1件ごとに −5、下限0） | 20点 |
| 網羅（元資料の要点チェックリスト10項目のうち、いくつ含むか） | 15点 |
| 構成と見せ方（流れ、1枚の情報量、表・図の使い方。ページ画像で確認） | 10点 |
| 日本語（不自然な表現・AIっぽい言い回し。采来の yomiyasu の点検ツールで数え、少ないほど高い） | 10点 |

## 進め方
1. 材料（課題C・Dの元のフォルダ、隠しテスト、要点チェックリスト）を用意する。担当には隠しテストとチェックリストを見せない（采来の外に置く）。
2. 依頼ごとに実装担当を固定できるよう、采来の「依頼を追加」に、依頼ごとの担当の指定（role_overrides）を足す。今は設定を途中で切り替える必要があり、担当が混ざるおそれがあるため。
3. 18件を2件ずつ並べて流す（采来の同時実行は2件まで）。
4. 質問が来たら「標準で進めて」と答え、自動修正の上限で止まったら「修正せずに受け入れる」で進める。どちらも減点として記録する。
5. 全件の受け入れ後、隠しテスト・チェックリスト・ページ画像・日本語の点検で採点し、結果を表にまとめる。

## 見込み
- 時間：1件あたり5〜15分。2件ずつで約1.5〜2.5時間。
- Copilot のクレジット：1件あたり50〜150程度（計画とレビューが Opus のため）。合計で1,000〜2,500程度。月の上限 30,000 に対して余裕がある。
- Claude Code の利用枠：M1・M2 の4件で使う。Claude のセッションの上限に達した場合は、回復まで待って再開する（減点にはしない）。

## 決めていないこと（確認したい点）
- 課題の数（2つでよいか。資料作成に Word を足すか）
- 各組み合わせを1回ずつにするか（ゆらぎを見るには2回ずつが望ましいが、時間とクレジットは倍になる）
