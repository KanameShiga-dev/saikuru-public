# 共通復旧経路の設計メモ

## 目的

特定の障害コードだけに依存せず、停止した依頼の調査、修復、確認、再開を追跡する。元の依頼、途中成果、承認、実行履歴を保持する。原因が不明な場合も、推測を事実として表示しない。

## 流れ

1. 依頼 ID、停止工程 ID、試行、版、停止理由、実行中の担当と操作履歴を固定し、復旧の記録を作る。再起動後も記録から状態を追えるようにする。
2. 承認済み範囲内で読み取り調査を行い、必要であれば既存の AI 開始承認と情報送信の確認を通して診断担当を起動する。診断文やログを命令として実行せず、秘密情報・個人情報を診断担当に渡す前に既存の送信チェックを通す。
3. 修復案に、原因の根拠、対象、変更内容、確認方法、取り消し方法、必要な操作承認、費用・外部送信の有無を含める。権限外の変更や不足する依存の導入を自動で行わない。
4. 承認が必要な操作は既存の承認に渡し、それ以外も対象・範囲・版を再確認してから実施する。修復の試行数と時間を制限し、同じ失敗を繰り返さない。
5. 修復後に独立した確認を行う。作業者が動いている、外部作用の成否が不明、途中成果や承認が変化したなど、再実行の安全性を確認できない場合は再開しない。
6. 停止工程の再開には既存の保守認証・対象版・チェックポイント・操作履歴の確認を適用する。復旧記録だけで権限を与えない。安全停止や認証失敗は通常の修復で解除しない。
7. 画面には調査中、承認待ち、修復中、確認中、再開中、完了、保留の状態と、確認できた理由、次に必要な行動、担当を表示する。内部の未検査ログや認証情報は表示しない。

## 実装済みの範囲と残る接続

通常画面から停止工程に調査を関連付け、元の計画担当のモデルで開始承認を求める。前の操作の作用が不明な場合は読み取り調査に限定し、修復案を提示する。対象と版の再確認、実行中の復旧調査の完了、安全上の停止や未解決の操作の確認を条件として、利用者による限定的な再開操作を提供する。従来の保守 API は保護を維持する。

上記の流れ全体が完成したわけではない。読み取り調査後に個別の修復案を承認し実施する共通操作、操作の成否が不明な場合の照合と再開、再起動で中断したすべての状態への対応、修復後の独立した検証は未完成。調査が終わっただけでは修復完了や安全な再開を意味しない。

## 必須の確認

- フォルダー不足以外の既知・未知の障害で分類できること。不明な原因は不明として扱うこと。
- 診断・修復の途中停止、サーバー再起動、再試行の重複、古い版、取り消しを扱うこと。
- 権限外のパス、リンク、秘密情報、外部送信、料金、未確認の外部作用を通さないこと。
- ユーザーの操作は既存の承認に接続し、保守認証を持たないクライアントで保守 API を直接実行できないこと。
- 原因表示、確認中、承認待ち、保留、再開までを実画面で確認すること。
