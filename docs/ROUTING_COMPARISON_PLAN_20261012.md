# 采来の軽い経路：小規模比較計画（2026-10-12）

## 問いと判定対象

対象は `ROUTING_VALUE_REVIEW_20261012.md` の単一制作・明確な合格条件を持つ架空の新規依頼に限定する。問うのは「計画用AI呼び出しを省くと、安全と品質を保った通常受領1件あたりの**全工程**のトークンと人の介入が減るか」。計画工程のトークンだけを節約額にしない。

| 比較 | 条件 | 言えること |
| --- | --- | --- |
| 主比較 | 采来・通常経路 F 対 采来・軽い経路 L | 同一の采来、モデル、レビュー、権限、課題で計画工程を省く効果を評価する |
| 実用比較 | 直接CLI D 対 F・L | 利用者が依頼方法を選ぶ際の総費用・品質・操作負担を比較する。CLI固有の承認・履歴・復旧の差が残るため、経路だけの因果効果とは呼ばない |

既存の16件の試行、2026-10-11の文脈予算ON/OFF計測、添付資料のCLI単発比較は設計上の参考値であり、この比較の対照群にはしない。特に文脈予算1000文字での削減率は現在の軽い経路へ流用しない。

## 試作を始める前の条件（AI費用ゼロのゲート）

1. 分離した評価用プロセス・DB・ポート・架空プロジェクトを用意する。通常サービスのDB、ポート、実案件、ホーム内の秘密、実業務添付を参照しない。ソース・設定・CLI版・採点器・課題の指紋を記録する。公開用レポートには実パス、本文、アカウントを含めない。
2. 軽い経路を明示選択式の試作として追加する。既定は通常経路。`auto_execute=true`、変更範囲と合格条件の明示、単一制作担当、添付なし、`security_review=always` を必須とする。認証・権限・公開・削除・機密情報・調査や担当交代を含む依頼は拒否して通常経路を案内する。受付分類だけで自動選択しない。
3. Lは計画用AI呼び出しだけを省き、制作→通常レビュー→セキュリティレビュー→利用者受領、操作承認、ファイル範囲、修正上限、停止・再開、`pending_checks` を既存経路と共用する。レビュー省略や安全設定の緩和を加えない。途中で不明点が出たら停止し、編集後の自動経路変更はしない。
4. 外部モデルを呼ばない分離テストで、Fでは計画が呼ばれLでは呼ばれないこと、両経路で制作後に2種のレビューが作られること、対象外依頼がLに入らないこと、拒否・停止・修正上限・未確認事項・条件付き受領が同じ判定になることを確認する。モックの合格を実AIや画面の合格と呼ばない。
5. 計測器を修正または評価用集計を独立に作る。現行 `team_optimization_metrics.py` は `accepted_with_pending_checks` を accepted に含むため、そのまま成功率に使わない。工程ごとの全呼び出し、失敗と再試行、usage欠損、実効モデル・effort、cache read/create、経路、停止理由を記録できることを分離データで確認する。

このゲートを満たさなければ、実AI試行へ進まない。試作の変更範囲は `server.py`／依頼画面、`team_engine.py` の新規依頼入口と状態遷移、保存・評価用集計、および必要な分離テストに限定し、稼働サービスには反映しない。

## 固定する実行条件

- 架空の小さなPython不具合修正を1題用意する。初期スナップショット、指示、許可ファイル、成果物、独立テスト、受領条件を固定し、各試行は新品の複製から開始する。答えや先行試行の成果を後続へ渡さない。
- FとLは同一の利用可能なモデル／effortを全工程で使用する。初期候補は `gpt-6-sol`／medium。Dでも同じモデル／effortを選ぶ。実効モデルとeffort、CLI版、プロバイダーの利用量の取得可否を実施日に確認し、揃わなければ比較を止める。高effort・Astra・Fastは使わない。
- FとLの権限、実行道具、通常・セキュリティレビュー、修正上限、時間上限、経験・Skill、文脈予算、画像化、承認手順を固定する。文脈予算は実際の削減をしない同一設定にし、他の最適化を同時に変更しない。
- Dにも同じ許可範囲と独立採点を課す。D固有の承認、レビュー記録、復旧機能の有無と人の操作は別表で記録する。Dの代理操作時間を人間の実測時間として表示しない。
- 実行は逐次、順序は事前登録する。反復時はF→LとL→Fを入れ替え、キャッシュ状況と他作業の同時実行を記録する。条件間で問題文や採点器を修正した場合、その組は比較から除外して費用を残す。

## 段階と費用上限

| 段階 | 実施内容 | 進行条件 |
| --- | --- | --- |
| 0 | 上記の分離試作、非AIの境界確認、採点器・計測器の確認 | 安全・記録・採点がすべて通る |
| 1 | 同一課題でFとLを各1回、逐次実行する予備対比較 | 独立採点、受領状態、usageが両方確定し、安全差がない |
| 2 | 段階1に問題がなければDを1回実行し、実用上の選択肢を確認 | Dの権限差と人の操作を明示できる |
| 3 | 別途決めた予算内でF/Lの順序を逆にした対比較と、必要なら別課題を追加 | 反復後にのみ限定的な採否を判断する |

段階1の1組は**予備測定**であり、削減率や採用を確定しない。過去の1依頼は数十万トークン規模で、3経路の単発でも大きな利用量になり得る。実行前に総トークン・利用枠・時間の硬い上限と、各段階後の継続判断を数値で設定する。上限未設定のまま段階1へ進まない。上限到達、認証・利用量取得の異常、権限や秘密の逸脱、採点条件の不一致、評価環境の混入があれば新規試行を停止し、失敗と消費を保存する。同条件を黙って再試行しない。

## 記録と分析

| 指標 | 定義・注意 |
| --- | --- |
| 主指標 | 当該条件の全試行・全工程の入力＋出力トークン（失敗・修正・再試行を含む）÷独立採点に合格し、必須確認が完了して通常受領した件数。0件または必要なusage欠損時は算出不可 |

| 品質・安全 | 独立テスト、差分の範囲、余計な編集、必須確認、承認・権限違反、レビュー指摘、修正回数を条件ごとに記録 |

最初の3試行は表と工程別内訳を提示し、差と失敗理由を列挙する。統計的な優位や一般的な削減率は主張しない。反復後も課題別の対差、範囲、条件付き受領・停止率を併記する。LがFより安くても、品質低下、安全違反、必須検証の欠落、修正や人の介入の増加があれば採用しない。Dが同等以上なら、その依頼種別で采来を使う追加価値（承認・履歴・復旧等）が実際に必要かを判定する。差が小さい、ぶれる、または測れない場合は通常経路を維持する。
