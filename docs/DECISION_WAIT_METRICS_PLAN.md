# 実装計画：人の判断待ち時間の計測（勤務時間内のみ計上・A案）

作成日：2026-10-03　対象：`C:\Projects\Projects\Operations\agent-team`　状態：**実装済み（検証範囲は DECISION_WAIT_METRICS.md を参照）**（2026-10-03 利用者が下記8章の3点を決定）。実装担当：Codex

## 1. 目的と計測の定義

- 人の判断待ちのうち、**勤務時間（既定：平日 9:00〜18:00、日本時間）に重なる部分だけ**をボトルネック指標として計上する。
- 勤務時間外の待ちは捨てずに「時間外の待ち（参考）」として別に保持する。
- 計測は表示専用。判断の期限、通知、担当選択、承認の可否には使わない。

| 指標 | 定義 |
|---|---|
| 勤務時間内の判断待ち | 判断待ち区間と勤務時間帯の重なりの合計（ボトルネック指標） |
| 時間外の判断待ち | 判断待ち区間の長さ − 勤務時間内の判断待ち |
| 依頼全体の所要時間 | 依頼の作成から受け入れ・中止までの実時間（参考） |

| 事実 | 根拠 | 計画への影響 |

## 3. 設計

### 3.1 設定（`team_config.py`）

```json
"business_hours": {
  "utc_offset_minutes": 540,
  "start": "09:00",
  "end": "18:00",
  "workdays": [0, 1, 2, 3, 4],
  "holidays": []
}
```

- `workdays` は月曜=0。`holidays` は `"2026-11-03"` 形式の日付の一覧で、手動で登録する（祝日の自動計算は今回の対象外）。
- `validate_config` で検査する：時刻の形式、`start < end`、オフセットの範囲、日付の形式、休日は最大400件。
- 設定がない既存の `config.json` は既定値で補う。既存の設定は書き換えない。

### 3.2 勤務時間の計算（新規 `team_worktime.py`、純粋関数）

- `split_seconds(start, end, cfg) -> (inside, outside)`
  - +09:00 の日付ごとに、`[start, end]` と当日の勤務時間帯 `[9:00, 18:00]` の重なりを合計する（勤務日かつ休日でない日だけ）。
  - `end` が `None`（判断待ちが継続中）のときは、呼び出し側が渡す現在時刻で計算する。
  - `end < start` は 0 を返す。日付の走査は最大400日で打ち切り、超えた場合は「計算範囲外」とする（記録の異常に備える）。

### 3.3 状態の変化の記録（`team_store.py`）

- 新しいテーブル：`transitions(seq INTEGER PRIMARY KEY AUTOINCREMENT, kind TEXT, id TEXT, job_id TEXT, from_status TEXT, to_status TEXT, at REAL)`
- `Store.put` で、`kind` が `job` か `task` で `status` が変わったときだけ1行を追加する。
  - 既存の行の読み取りと書き込みは同じロック・同じトランザクションの中で行う。
- 既存データの移行は不要（`CREATE TABLE IF NOT EXISTS`）。導入前の依頼には変化の記録がない。

### 3.4 判断待ち区間の組み立て（新規 `team_waits.py`）

- **待ちの状態**
  - 依頼が `blocked`・`awaiting_approval`・`awaiting_acceptance` のとき
  - 工程が `awaiting_approval`（ツール操作の承認待ち）のとき
- **区間の結合**：同じ依頼の中で重なる区間は1本にまとめ、二重に数えない。
- **区間の終了**：待ちでない状態に移ったとき、または `cancelled`・`accepted` になったとき。
- **待ちの種類**：区間が始まった時点の情報で分類する。
  - 未処理の承認があれば、その `kind`（`plan`・`tool`・`question`・`completion`・`context_conflict`）
  - なければ直前のイベント（`repair_limit` など）
  - どちらもなければ「その他の停止」
- **再起動による中断（`interrupted`）**：システムが原因の停止なので「システム停止」として別に集計し、既定ではボトルネック指標に含めない。
- **導入前の依頼**：「計測開始前」と表示する。承認記録の `created_at`〜`decided_at` だけを使った参考値を出す場合は、「承認記録のみの近似」と明記する。

### 3.5 API（`server.py`・`team_history.py`、読み取り専用）

- `/api/project-history?job_id=...` の応答に `waits` を追加する。
  - 各区間：`opened_at`・`closed_at`・`reason`・`inside_seconds`・`outside_seconds`・`open`（継続中かどうか）
  - 依頼ごとの合計
- 新規 `/api/decision-wait-stats?from=&to=`
  - 判断の種類ごとに：件数・中央値・90パーセンタイル・最大値（勤務時間内）
  - 時間外の合計と、計測開始前の件数
- 既存のローカル画面認証を使う。AIへの呼び出しや外部への送信はしない。

### 3.6 画面（`web/history.js`・`history.html`・`history.css`）

- 依頼の詳細に「人の判断待ち」欄を追加する。
  - 勤務時間内の合計と、時間外の合計（参考）を表示する。
  - 区間ごとに、種類・開始・終了・勤務時間内の時間を一覧で表示する。
- 時系列に「人の判断待ち」の行を追加する。勤務時間内は塗りつぶし、時間外は斜線で区別し、文字でも表記する。
- 履歴画面の上部に、期間内の集計（種類別の中央値・最大値）を表示する。
- 勤務時間の設定値は画面に表示する。設定の編集画面は第3段階で検討する（それまでは `config.json` で設定する）。

- **導入前の退避**：変更する既存ファイルを `data/backups/decision-wait-<日時>/` に退避する。DBは `team_ledger.py backup` と同様の手順でバックアップを取る。
- **再起動**：実行中・待機中のタスクがないことを確認してから行う（既存の運用手順に従う）。
- **戻し方**：サービスを停止し、退避したファイルを元に戻して起動する。追加した `transitions` テーブルは残っていても既存の動作に影響しない。消す場合は、DBのバックアップから戻す。

## 7. 対象外・残るリスク

- **対象外**：
  - 勤務時間外の通知の抑止と朝の一覧通知（計測とは別の計画にする）
  - 人ごとの勤務時間（利用者ログインが前提）
  - 祝日の自動判定
  - 昼休みの除外
- **導入前の依頼**：正確な待ち時間を出せない。
- **時刻の誤差**：PCの時計がずれていると誤差が出る。サーバーの停止中も待ちとして数える（人の対応待ちであることは変わらないため）。
- **期限切れの扱い**：ツール操作の承認が15分で切れる仕様は変えない。夜間の運用への影響は、計測の結果を見てから別途判断する。
- **分類の精度**：待ちの種類の分類は、区間が始まった時点の情報で決めるため、途中で種類が変わった場合は反映されない。

## 8. 決定事項（2026-10-03 利用者が決定）

1. 休日の初期値は空（土日のみ休み）。祝日は後から `holidays` に追加する。
2. 再起動などによる中断（`interrupted`）は、ボトルネック指標から除外し、「システム停止」として別に集計する。
3. 導入前の依頼は、承認記録だけの近似値を出さず「計測開始前」と表示する（期限切れ後の停止を取りこぼし、実態より短くなるため）。
