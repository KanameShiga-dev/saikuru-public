## 経緯（なぜ変えたか）

1. 社内向け資料の作成の中で、采来のUIを評価した。良い点（状態を色と名前で示す、送信前の確認、取れない値を「不明」と表示、AIの報告と人の判断の分離）は維持する。
2. 課題は「人が対応すべき判断が画面の中で埋もれる」こと。原因は、機能を足すたびに上へ積み、優先順位の軸がなかったことにある。
   - ボードが画面の下から始まり、判断の通知が浮いてカードに重なる
   - ヘッダーで画面の移動・普段の操作・危険な操作（全作業を中止）が混在
   - 利用枠の残量が折りたたみの中
   - 文字サイズが15種類（10〜12pxが約19か所）、色が固定値でダーク表示がない
   - 台帳の詳細がダイアログで、その中からさらにダイアログが開く
   - 履歴の時間軸が両端だけで、詳細がページの最下部に出る
3. 改善案をHTMLのサンプルで示し（`docs/design/20261003-consultation/20261003_采来UI改善案_*.html`）、利用者が「まずUIの改善を実施、それ以外は別途」と決定した。
4. 作業中に、**自動修正の上限で止まった依頼が「あなたの判断」にも通知にも出ない**という以前からの不具合を見つけ、利用者の承認を得て修正した。

## 決定事項

- 采来本体に今回入れたのはUIの改善だけ。判断待ちの計測（A案）、判断画面（判断材料と選択肢）、通知の拡充は別作業（「次の作業」を参照）。
- 処理の結び付き（要素ID・APIの呼び出し・承認と確認のチェック・送信内容の表示）は変えない。見た目と配置だけを変える。
- 色は `web/theme.css` の変数だけを使う（固定の色コードを各画面のCSSに書かない）。

## Codexへの作業上の注意

- 新しい画面や部品は `web/theme.css` の変数（`--surface`・`--text`・`--green`・`--amber-*` など）を使う。固定の色コードを足すとダーク表示が崩れる。
- 新しい静的ファイルを足すときは、`server.py` の `files` と `mobile_gateway.py` の `VALID_PATHS` の両方に追加する（今回 `theme.css` を足した直後、再起動前の本番で404になり色が崩れた）。
- 一括で置換するときは、CSSのプロパティ名に注意する。今回、色の `white` の置換が `white-space` まで壊した（修正済み）。
- 作業ボードの判断待ちは `decisionItems()` が唯一の入口。バナー・タブのタイトル・PC通知・音声通知はすべてここから作られる。
- 台帳の詳細はダイアログではなくなった。「開いているか」の判定は `!$('editor').hidden`。
- HTML・JS・CSSはリクエストのたびにディスクから配信されるため、`web/` の変更は再起動なしで本番に出る。Pythonの変更だけが再起動を要する。

## 人間中心の観点

- 判断待ちを最上部に常設し、浮いた通知で内容を隠さない。バナーは判断が済むまで消えない（閉じても判断待ちが残る、という従来の意味を表示でも保つ）。
- 状態は色だけでなく、記号（▶ ！ × ◷ ✓）と名前で示す。危険な操作は「⋯」メニューの区切り線の下と、台帳の赤枠に分離した。
- 取れない値は「不明」「未取得」「未記録」のまま表示し、推測しない。
