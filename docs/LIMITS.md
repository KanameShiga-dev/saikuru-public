# 制約と本格採用の条件

ローカルで動く初期版。全面採用の完了とは判定しない。
Claude単独CLIのログインと、両者の実タスク・ネイティブ承認の連携確認が残っている。

## 境界

- ループバック限定。Host/Origin検査、SameSite Cookie、操作用ヘッダーで通常の他サイトからの操作を拒否する。
- ワーカートークンは自分の操作確認用で、ブラウザの承認とは区別する。
- 同じWindowsユーザーの任意コードはDBやサービスに到達し得る。管理者強制やOSによる隔離ではない。
- Claudeはrestrictedとツール前フック、Codexはネイティブ承認とサンドボックスを使用。境界や承認粒度は同一ではない。
- Codexがネイティブで許可する操作全てに承認カードが出るわけではない。
- 広い検索や承認済みコマンドが読む全ファイルの機密性を判定する仕組みはない。送信できるプロジェクトだけを対象にする。
- 公開・push・課金・認証情報取得・対象外変更などは禁止指示を渡すが、自然言語の指示だけで完全強制できるとは扱わない。

## 運用制約

- 同一プロジェクトの直列化はこのサービスからのタスク間のみ。他のDesktopや端末からの編集は検知しない。
- 作業ごとのworktreeや専用Windowsユーザーは未導入。
- 正常停止・取消では作成したCLIツリーを終了する。統括の強制終了時に子プロセスが必ず終了する保証はまだない。
- 異常終了後はプロセスとファイル差分を確認してから再試行する。DBの状態復旧だけで作業の復旧完了としない。
- 担当が自由に子エージェントを増やす方式ではない。計画・依存順・プロファイルに従う自動分担。
- Gitチェックポイント、実機受入、稼働中サービスの停止・デプロイは自動化していない。

## 次の段階

1. ClaudeログインとCodex→Claude→Codexの実往復。
2. 両CLIの本物の承認要求で、許可・拒否・取消・期限切れを検証。
3. 強制終了時の子プロセス回収と、外部作業との競合防止を強化。
4. Gitチェックポイント・隔離作業場所・差分確認を統合。
5. モデル適合試験を画面から実行し、合格後に役割へ採用できる仕組みを追加。
6. 既存方針共通化・フォルダ再編は別途承認された計画に沿って適用。
7. 常駐運用の自動起動・障害通知・保守を決める。

これらが未確認の間は、専用サンプルフォルダでの試行を基本とする。
