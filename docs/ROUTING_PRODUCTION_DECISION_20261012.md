# 采来の経路比較に基づく本番改修方針（2026-10-12）

状態：方針決定。通常サービスの経路・設定・セキュリティ方針は変更していない。公開・pushなし。

## 決定

**軽い経路を本番の一般依頼へ導入しない。** 評価専用の明示選択と設定ガードを維持し、通常依頼は現行の計画付き経路を既定にする。初回の架空の単一ファイル修正では軽い経路が通常経路より3組すべてで少ないトークンを使い、独立採点と代理受領に合格した（合計489,273対328,628、-32.8%）。[初回比較](ROUTING_COMPARISON_RESULTS_20261012.md) 追加の文字列修正2組でも両経路が合格し、軽い経路の取得済みトークンは20.8%少なかった。実利用者の条件付き受領と資料作成時のレビューによる不備発見は一部確認できたが、再受領、資料の最終受領、継続運用は未確認。[追加評価](ROUTING_ADDITIONAL_EVALUATION_20261012.md)

采来の目的は、**人が必要とする引き継ぎ・レビュー・承認・復旧を伴う仕事を、未確認事項を隠さず完了へ運ぶこと**とする。トークン削減は同等の成果と受領が得られる場合の効率指標であり、采来を使うこと自体を目標にしない。直接Claude CLIは同じ小課題を23,683トークンで独立採点に合格したが単発で、采来のレビュー・承認・履歴・復旧は含まない。この差を一般的な削減率や品質差として扱わない。

## 利用者が選ぶ入口

| 選択 | 適用条件 | 伝えること |
| --- | --- | --- |
| 直接CLI | 範囲・合格条件が明確な単独の小作業で、采来の引き継ぎ・レビュー・承認・復旧を必要としない | 采来の外で利用者が選ぶ。采来の承認・レビュー記録が付くと表示せず、CLI固有の権限・確認に従う |
| 采来の通常経路 | 要件整理、複数工程、担当交代、添付・資料、未知の依存、リスク、追跡可能なレビューや受領が必要 | 現在の既定。計画・制作・通常レビュー・既定のセキュリティレビュー・利用者受領を維持する |
| 采来の軽い経路 | 現時点では隔離評価のみ。将来の候補は明確な単一制作依頼で、采来のレビュー・承認が必要なもの | 本番入口には出さない。分類結果だけで自動選択しない |

迷う場合は通常経路とする。機密情報、個人情報、認証・権限、外部送信・公開、削除、重要データ移動を含む依頼は軽い経路の候補にしない。既定の`security_review=always`と既存の承認・ファイル範囲を維持する。レビュー省略は今回の決定に含めない。

## 改修の優先順

1. **受領証拠の整合**：未確認項目ごとに対象、要求された検証、証拠、提出時刻・出所、確認結果を結び付ける。レビュー後に証拠が届いたときは影響する項目を再評価し、受領画面へ反映する。条件付き受領を証拠の追加だけで通常受領へ自動昇格させず、利用者が更新内容を確認して再受領する。証拠のない項目や停止済み担当の必須検証は未確認のまま残す。予備試行で証拠提出順による条件付き受領を確認したため、これは軽い経路の本番導入前に必要。**実装状況**：受領待ちまたは条件付き受領の最新判断に限り、利用者が未確認項目を一つ指定し、根拠と実施確認を記録できる。元の判断を保全して新しい受領判断を作り、再受領までは`awaiting_acceptance`とする。レビュー指摘は残す。AIによる独立した証拠検証や既存の全案件への自動再採点は未実装。
2. **効果計測の整合**：`accepted`と`accepted_with_pending_checks`を別集計にする。成功単価は独立採点合格かつ通常受領を分母とし、途中失敗・中止・再試行を含む全消費も併記する。usage欠損はunknownとし0で補わない。工程別トークン、修正回数、未確認項目、利用者の介入回数・待ち時間を経路別に記録する。**実装状況**：`team_optimization_metrics.py`では通常受領・条件付き受領・状態別件数を分離し、全試行の利用量がfinalのときだけ「通常受領1件あたり」を出す。経路別・工程別の取得済み量、修正回数、未確認件数、承認待ち時間も示す。DBには独立採点の合否と人の実作業時間がないため、独立採点合格1件あたりの主指標と人の負担の実測は別途評価で扱う。
3. **追加評価**：固定したモデル・effort・道具・権限で、複数の代表的な依頼種別と意図的な不具合を含むケースを直接CLI・通常経路・軽い経路で比較する。利用者本人による画面操作、証拠の後出し、停止・再開、承認の判断と所要時間、レビューの実欠陥発見を確認する。セキュリティ・プライバシーの逸脱、余計な編集、条件付き受領の増加を見逃さない。結果は成功例だけを抽出せず全試行で示す。**進捗**：文字列修正2組と実利用者の条件付き受領は確認済み。資料作成は修正後に独立採点合格したが予算停止で最終受領なし。残る実利用者の再受領、資料の直接CLI比較、意図的な欠陥の固定試料は未完了。
4. **導入の再判断**：前3項目を満たし、特定の依頼種別で通常経路と同等の合格・受領・安全性が得られ、全試行を含む通常受領1件あたりの費用または人の負担が実用上改善した場合だけ、利用者の明示選択による限定導入を別途提案する。自動振り分けと既定ONは別判断とする。導入時は停止条件、監視指標、設定をOFFに戻す手順を先に用意し、進行中の案件を自動移行しない。**今回の再判断**：[限定導入しない](ROUTING_LIMITED_ROLLOUT_REDECISION_20261012.md)。小課題の効率改善は再現したが、受領・安全性・回復の根拠が不足する。

## 判定で避ける誤り

- 今回の3組は1種類の架空課題であり、レビューが欠陥を防いだという証拠ではない。通常経路のレビュー消費は242,249/489,273、軽い経路では202,239/328,628。費用が大きくても、保護効果を測る前にセキュリティレビューを削らない。
- 予備試行の`accepted_with_pending_checks`を通常受領の成功数へ混ぜない。証拠が後から届いた場合の確認と人の再受領を別の操作・記録として扱う。
- 直接CLIと采来を異なる承認・レビュー条件のまま比較した差を、計画工程だけの節約として解釈しない。
- 評価ランナーの代理受領を実利用者の受領と呼ばない。隔離画面での実利用者の条件付き受領は別に記録したが、待ち時間、操作負担、安心感は未測定。

## 実施境界と復旧

本書は改修と採用の判断基準であり、1〜4の実装や本番導入が完了したことを意味しない。現行サービスは評価用設定を入れない限り通常経路のまま。将来の限定導入で異常が出た場合は新規依頼の軽い経路の選択を無効化し、既存の記録・案件を削除せず個別に未完了ゲートを確認する。公開やpushは別途明示依頼を受け、送信前に個人情報・機密情報を厳格に確認する。
