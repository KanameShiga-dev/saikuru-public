## 結論

1. **案Dは採用可能。ただし P0 全体を無効にする意味と影響を明記し、G2/G3・安全レビュー・通常の利用者承認は維持する。**
2. **案Aは、保守トークンを通常UI操作全体に流用せず、対象を検証する専用の「利用者による再開」APIとして実装するなら妥当。**
3. 本番の P0 無効化は設定だけで済むように見えても、新規依頼が従来経路へ切り替わり、復旧・失敗時の挙動と完了保証が変わる。コード・テスト・利用者向け説明を揃えた後に、本番固有設定として適用する。
4. P0 無効化は既存ジョブを変換しない。ジョブ作成時に確定した契約バージョンを最後まで保持する。

## 1. 案D：P0契約の設定切替

### 推奨仕様

- `p0_contract_enabled` を真偽値設定として追加する。
- 既定値は `true`。キーがない既存設定も `true` として扱い、意図しない一括切替を防ぐ。
- `false` は新しく作る通常の `route == 'full'` 開発依頼にのみ適用し、ジョブ作成時に一度だけ評価する。
- `true` で作成した既存ジョブは、その後設定が `false` になっても P0 のまま扱う。逆方向にも既存ジョブを遡及変更しない。
- 設定値が欠落・不正な場合は `true` 相当の暗黙処理ではなく、既存設定互換を保ちながら明示的に検証する（型不正は起動・保存時に拒否）。
- 本番で `false` にする場合は本番の `config.json` のみに適用する。ソース既定値や共有設定を `false` にしない。

### P0を無効にしても維持するもの

- G1での登録と G2（AI計画作成開始）の明示承認、指紋・版・試行回数の照合。
- G3（開発計画の利用者承認）。計画の承認前に実装を開始しない。
- 通常レビュー、安全レビュー、利用者の承認・正式受領、既存の秘密情報・外部通信・削除のガード。
- `route == 'light_eval'` の隔離条件と、資料作成専用経路の既存動作。
- `code_test_contract_version` など、P0のオン・オフとは別に設定されている検証要件。

G2はジョブ作成時に `g2_gate_version=1` を設定して `_request_g2()` を呼び、スケジューラーもこのゲートを共通に検証している。G3は計画タスクの成功後に共通で `plan` 承認を作成する。したがって、P0フラグはこの2ゲートを条件分岐させない。

### P0を無効にした場合に変わるもの

`p0_contract_version` / `goal_contract` を付けず、既存の非P0経路で動く。現在の実装では、P0ジョブに限定された失敗停止・保守再開要求・自動フェイルオーバー抑止・利用量上限後の自動再試行抑止・P0の進捗/成果物/完了条件の検査が適用されない。これは画面表示だけの切替ではなく、**新規ジョブの実行・復旧・完了保証の切替**である。

従って、利用者向けに「P0を使わない」とだけ表示せず、少なくとも次を説明する。

- 既存の G2/G3 と通常レビューは残る。
- P0の目標契約、細かな進捗表示、P0固有の停止・復旧・成果物の確認条件は、その設定で作った依頼には適用されない。
- 非P0の既存復旧挙動が使われ、認証切れや実際に返った利用量上限を契機に Provider を自動切替する経路が有効になる。これは利用量を予測して依頼を拒否する処理ではない。Claude/Copilot 間の切替は、2026-10-15 の利用者決定として、データ分類が Public/Internal の場合に限り、切替先がその担当で有効かつ利用可能な場合に行う。Codex へは切り替えない。これは利用者が最初にモデル/Effortを選ぶ方針と両立する既存の復旧方針であり、本番適用にあたり新たな方針承認は不要。
- 設定変更後に作った依頼だけに効く。設定変更前の依頼は変更されない。

### 案Dの受入条件

1. fresh config の既定値と、キーのない旧 config の既定値は `true`。
2. `false` は真偽値のみ受理。文字列・数値は拒否。
3. `false` で作成した full-route ジョブに P0マーカー/目標契約がなく、G2とG3の承認が引き続き要求される。
4. `true` で作成したジョブは設定切替後も P0マーカーを維持し、逆方向の切替でも既存非P0ジョブにマーカーを追加しない。
5. document / light_eval 経路の既存条件が変わらない。
6. P0オン・オフの境界で、通常レビュー・安全レビュー・秘密情報保護・外部通信/削除ガード・正式受領が弱まらない。
7. 起動時の設定と、依頼作成時に採用された契約を後から監査できる（設定変更イベントに値を記録し、ジョブに採用バージョンを保持する）。

### 重要な実装分離

現在 `p0_development = not document_source and route == 'full'` が `p0_contract_version` の付与を決めている。設定を足す際は、同じ `p0_development` 判定を一貫して使用する一方、G2/G3や独立の検証契約をその判定に誤って含めない。`team_engine.py` の各 `p0_contract_version` 分岐を一覧化し、受入条件に対応づける。

## 2. 案A：通常UIセッションからの限定再開

### 認可判断

現在の `agent_team` Cookie はプロセス起動時に生成され、`HttpOnly`・`SameSite=Strict` で通常UI操作を認証する。ログインや個人別ロールはなく、このCookieは「このローカルUIセッションを操作できる人」を示すだけで、別人確認済みの保守担当を識別しない。

よって、UIセッションを保守トークンそのものとして扱うことや、ブラウザーから `intended_role: maintainer` を送らせる設計は不適切。一方、単一利用者のループバック専用アプリにおいて、利用者が具体的な変更内容を確認して自ら再開する限定APIに通常UI認証を使うことは、利用者本人の操作として合理的である。UI文言は「保守担当として」ではなく、実際の認証主体に合わせて**「停止中の作業を確認して再開」**等とする。監査記録の actor は固定値 `authenticated_local_app_session` とし、クライアント指定を受け付けない。

### 推奨するAPI境界

- 既存の `/api/retry` と `/api/tasks/model` の保守トークン要件を外さない。
- 専用のPOST操作を追加し、通常の `authorized()` と `X-Agent-Team-UI: 1` を必須にする。既存のJSON限定、サイズ上限も維持する。
- 専用操作は「このジョブの、この中断担当を、利用者が確認した上で再開」に限定。`/api/maintenance/state`、保守診断詳細、`intended_role=maintainer` の承認は従来どおり保守トークン必須。
- サーバー側で毎回、ジョブが P0、状態が `maintenance_required`、中断担当IDと再開対象が一致、担当が再試行可能、キャンセル/完了済みでないことを再確認する。ブラウザーからの job/task/role 情報を信頼しない。
- リクエストは明示的な `checked_changes` と `confirmed` を要求し、確認文と対象ジョブ・担当・選択モデルを画面に示す。確認文は誤操作防止であり、認証やロール証明の代用ではない。
- 同じ操作の二重送信は一度だけ適用する（状態遷移の原子的検証または一回限り nonce/再送識別）。再開後は既存の試行番号・G2の再要求・成果物検証・安全ガードを維持する。
- モデル切替を再開に含める場合は、サーバーの `ModelCatalog.validate()` で検証済みの `{adapter, model, effort}` のみ受け付ける。対象担当だけを切り替え、他の待機担当へ波及させない。プロファイル変更と再開を1トランザクションで監査記録する。
- 再開イベントに actor、対象、変更前後のモデル（秘密値なし）、確認フラグ、時刻、結果を記録する。プロンプトや認証情報をイベントへ複製しない。

### Cookie運用上の条件

- アプリは現状どおり `127.0.0.1` にのみ bind する。LAN公開・トンネル公開・リバースプロキシ公開を認めない。
- 状態変更POSTは `Origin` がアプリの完全一致Originであることを必須にし、`Sec-Fetch-Site` が存在する場合は `same-origin` のみ許可する。現行 `common()` はOrigin欠落を許すため、再開操作を追加する際は少なくとも当該APIで欠落Originを拒否する。これと既存のHost確認・JSON・カスタムヘッダーを併用する。
- UIセッションCookieは `HttpOnly`・`SameSite=Strict` のまま。HTTPS終端がないループバックHTTPのため `Secure` 属性は現行構成に適用できない。これはローカル同一ユーザーのマルウェアやブラウザー拡張を排除する防御ではない。
- 再開APIに maintenance cookie/token を発行・保存せず、Cookieをワーカー子プロセスへ渡さない。

### 案Aの受入条件

1. 正規UIセッションから、対象条件を満たす停止ジョブだけ再開できる。
2. Cookieなし、別Origin、Origin欠落、クロスサイトFetch、CSRF様式の要求、UI用ヘッダー欠落は拒否され、状態不変。
3. task/jobの不一致、別ジョブのtask、別状態、再開対象不一致、完了/中止済み、二重送信は拒否され、状態不変。
4. ブラウザーが maintainer role や actor を偽装しても権限を得ない。
5. 一般 `/api/retry`、保守診断、保守承認の認可は緩まない。
6. 承認待ち時間・タスク実行時間の既存計時規則を保ち、再開で実行時間上限を不当に消費/延長しない。
7. 同じ故障を再度起こした場合は、既存の回数上限・保守停止へ戻る。無限再試行にしない。
8. 既定モデルのままの再開と、利用者が選んだ有効なモデル/Effortへの切替を別々に確認する。利用量予測で自動停止させない。

## 3. 作業順と判断点

1. P0オフのコード実装は `d0260f9`（設定切替）・`df63470`（従来形式の進捗表示）で統合済み。Provider切替は2026-10-15に決定済みの範囲として扱い、新たな承認待ちに戻さない。
2. Claude報告では固定コミット `3151b2b` の関連151件中、既知の7件（`7d9a00d` 時点でも同名で失敗）以外は合格。これは報告値であり、このターンでCodexが再実行した結果ではない。
3. 次の確認は、本番コード・データの隔離複製で、AI呼出しなしに新規依頼→G2 pending承認記録→G2承認→G3 `plan` 承認発行を通すこと。Claudeが実施予定として報告しており、結果待ち。
4. 本番への `p0_contract_enabled=false` 適用は利用者が承認済みだが、実行は未実施。先行する本番複製の予行演習後、利用者自身が端末で実行する手順を使う。予行演習は本番反映そのものではない。
5. 案Aの再開機能は別作業で、API/UI/認可テスト（正常・不正Origin・無Cookie・状態不一致・二重送信・モデル変更）が未完了。P0を再度有効化する場合は、機能準備後に本番設定変更を別途判断する。

## 4. このレビューで確認したコード上の根拠

- `team_engine.py`: 現状のP0判定はfull-routeかつ資料作成以外で無条件（`create_job`）。同時に `g2_gate_version=1` と `_request_g2()` を全ジョブに設定する。
- `team_engine.py`: planner成功時にP0判定と独立して `plan`（G3）承認を発行する。
- `team_engine.py`: `p0_contract_version` は失敗時の保守停止、自動フェイルオーバー/利用量再試行、進捗・成果物・完了条件など複数経路を制御する。
- `server.py`: `authorized()` は通常UI Cookie、`maintenance_authorized()` は別の `X-Saikuru-Maintenance` 能力。`/api/maintenance/state`・保守承認・P0再試行・P0担当モデル変更を分離している。
- `server.py`: UI POSTはCookieと `X-Agent-Team-UI` を要求するが、`common()` はOrigin欠落を拒否しない。新しい再開APIでは同一Originを必須にする必要がある。
- `server.py`: HTTPサーバーは `127.0.0.1` にbindする。
- `team_config.py`: configの `automatic_operations` は型検証されるが、現時点で `p0_contract_enabled` は未定義。

## 5. 既知のリスク（本番反映前に明示）

**Write/Edit の許可済み編集には、Bash の削除ガードとは別の復旧境界がある。** 現行経路は変更前のファイルを `data/file-backups/<task>/<uid>/before.bin` と manifest に退避するが、退避から戻す専用の画面・APIは確認できていない。空内容による上書きも拒否されない。よって退避ファイルが存在することだけでは、利用者がすぐ復旧できるとは扱わない。

本番反映前に、許可済み Write/Edit の意味と利用者への説明を確認する。P0切替や Bash 削除ガードだけでこのリスクが解消したとは扱わない。自動復元機能の実装は別作業とし、必要なら復旧手順・保持期間・復元対象の検証を別途定義する。関連するコード経路と限界は [`DELETE_OPERATION_GUARD_PLAN.md`](DELETE_OPERATION_GUARD_PLAN.md) に記録している。
