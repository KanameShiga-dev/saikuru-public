# 担当モデルの完了報告の扱い

## 共通の約束

全担当に、最終報告を指定のJSONスキーマに合うオブジェクトだけで返すよう依頼する。CLIがスキーマ指定を受け付ける場合は、その機能も併用する。受信後は采来が同じスキーマで検証し、必須項目の欠落や型の違いを成功として扱わない。モデル名やProvider名から報告内容を推測しない。

| 接続先 | 初回の形式指定 | 受信後の扱い |
|---|---|---|
| Codex | `outputSchema` と共通の依頼文 | 最終回答から完全なJSONを回収して検証 |
| Claude | `--json-schema` と共通の依頼文 | `structured_output` を優先し、使えない場合は結果欄と最後のassistant本文から完全なJSONを回収して検証 |
| GitHub Copilot | スキーマ本文を含む共通の依頼文 | 完全なJSONを回収して検証。従来形式の依頼では形の修正を同じ会話で1回依頼 |
| Gemini | スキーマ本文を含む共通の依頼文 | 完全なJSONを回収して検証。従来形式の依頼では形の修正を同じモデルへ1回依頼 |

前置きやコードブロックに包まれたJSONも、必要な項目と型がすべて合う場合だけ回収する。余分なキーは失敗理由にしない。自由文から成功・検証結果・成果物を采来が補作することはしない。

## 後続工程に必要な中身

- 計画担当は、目的・範囲の要約と、後続が実行できる担当種別・作業内容を返す。計画の成果物・受入条件と作業の対応はP0計画契約で検証する。
- 作業・調査・レビュー担当は、実際の状態、実施内容と到達点、確認項目ごとの結果、未確認の項目を分けて返す。作成・変更した成果物やテストがスキーマにある場合は、それぞれ場所と変更理由を返す。
- P0で`done`を返す担当には、空でない要約、`stage_complete: true`、空でない確認結果を必要とする。内容が欠けたJSONは後続へ流さない。未確認項目の存在は隠さず、受入時にも別途判断する。
- 停止・差し戻しの理由と利用者への質問は、それぞれの欄に記す。采来が空欄から成功や権限を推測しない。

形式が直せない場合は成果物と失敗理由を保持し、依頼を完了扱いにしない。P0の依頼では、Copilot・Geminiも自動の追加モデル呼び出しをせず、実行メモに従って利用者の判断を待つ。実Providerでの4経路の通し確認は行っていない。

E1の再試行では、Claudeの結果欄からJSONを回収できなかった。生の回答本文は保存されていないため、結果欄が空だったのか、本文に完全なJSONがあったのかは判別できない。次回以降は最後のassistant本文も同じスキーマで確認し、失敗時は内容を保存せず、各欄の長さと構造化結果の有無だけを記録する。
