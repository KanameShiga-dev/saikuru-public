# P0 UI確認の手順と記録（Claude担当 L1〜L4）

更新：2026-10-18。対象ブランチ：`p0/claude-ui`。状態：fixture とスタブでの確認まで。統合版 API・実 Provider・本人受領は未実施。

## 1. 確認の方法

架空の状態だけを返す読み取り専用のスタブで、標準画面を確認する。実データ・実 Provider・DB は使わない。スタブは `127.0.0.1` のみで待ち受け、変更の POST は全て拒否する。

```
python -X utf8 tests/ui/p0/stub_server.py --port 8891 --state tests/ui/p0/states/p0-states.json
```

- `tests/ui/p0/states/p0-states.json`：UI確認用の架空の状態（9件の依頼、受領待ち・未知の値を含む）。
- `tests/fixtures/p0/state.json`：Codex が管理する共有 fixture。UI からは読み取りのみ。
- スタブが補う項目（`profile`・`attempt` など、最小の fixture に無い項目）は、確認用の既定値で、契約ではない。

| 場面 | 期待 |

## 3. 確認結果（2026-10-18、スタブ + ブラウザー）

- 上の表の全場面で、期待どおりの表示を確認した。コンソールのエラーは、スタブが答えない旧来の API（`/api/jobs/previews`）への呼び出し以外に無し（スタブに空の応答を追加して解消）。
- キーボード：Enter と Space で技術詳細を切り替え。Enter で詳細（承認）が開き、フォーカスがダイアログ内に移る。Esc で閉じる。
- 読み上げ用の名前：表示中の操作要素 32 個すべてに名前がある。進み具合の欄は h2 → h3 → h4 の階層で、状態は文字と記号（✓ ○ ×）でも示す。依頼の受付・詳細・チーム設定のダイアログに `aria-labelledby` を追加した。
- 確認中に見つけた誤り：架空の完了承認の `pending_items` を文字列の配列で作ったため描画が失敗した（実際の形は `{title, note, checks[]}`）。データを直して解消。画面の不具合ではない。

- Codex の11状態の共有 fixture（受付・計画作成承認待ち・計画承認待ち・復旧中・安全停止・仕様確認待ち・成果物確認待ち・正式受領済み・旧形式を含む）でも、コンソールのエラー無しで表示できた。進み具合のカードは新形式の未終了9件、受領済みと旧形式は対象外。
- 契約の確認事項（解消済み）：以前の共有 fixture では、依頼の状態が `awaiting_acceptance` なのに `p0_progress.completion_status` が `in_progress` だった。Codex が `awaiting_user_acceptance` を返すよう修正し、3.2 で再確認した。

## 3.3 操作確認（2026-10-18、統合ブランチ `fa6c3bf` の複製 + `--allow-fixture-actions`、架空データ・Provider無効）

統合ブランチの一時複製を、操作確認モードで動かして確認した。統合作業領域には書き込んでいない。確認用ランタイムには、実データの形との差があり、その補正を複製だけに加えて続けた（下の「ランタイムの不足」）。

| 操作 | 結果 |
|---|---|
| 業務の質問に回答 | 承認が `approved`、依頼が `running`、担当が `queued`、カードが「実行中」になり、詳細が閉じる。判断バナーが減る。**確認できた**（担当の状態を実際の流れに合わせた後） |
| 確認根拠の記録（完了承認） | 古い完了承認が `superseded`、新しい完了承認が `pending`、未確認項目が 0 件。`record_completion_evidence` の目印が消える。**確認できた** |
| レビュー結果の確認 | サーバーが「通常レビューが完了していません。」と返し、画面は通知欄に表示。状態は変わらない。**拒否の表示を確認。受領までは進めなかった**（ランタイムの不足） |
| 正式受領 | **未検証**（上の拒否により、受領の入力欄まで進めない） |
| 差し戻し | 完了承認が `denied`、依頼が `blocked`。理由が空でも通った。画面のバッジは「停止中（次の動作をご確認ください）」で、判断バナーには出ない。**確認できた** |
| 依頼の中止（進み具合の欄から） | 依頼と担当が `cancelled`、進み具合の欄から消える。標準の詳細には「この依頼全体を中止」だけが残る。**確認できた** |
| AIによる計画作成の開始の承認 | サーバーが「G2承認が未処理ではないか、対象ジョブの状態が不整合です。」と返した。画面は通知。**未検証**（ランタイムの不足） |
| 開発計画の確認・承認 | 「処理に失敗しました。」。計画の中身が画面に出ない。**未検証**（ランタイムの不足） |

### この確認で見つけ、画面側で直したこと
- 標準画面の文言に残っていた内部の呼び名（G1・G2・G3）を、業務の言葉に置き換えた（8 か所。例：「AIによる計画作成を1回開始する」）。
- 新形式の依頼が `blocked` で、復旧・保守の分類も利用者の判断の項目も無いとき、バッジが「判断が必要」になり、判断バナーと食い違っていた。原因を推測せず「停止中（次の動作をご確認ください）」と表示する。
- 実行中の新形式の依頼の詳細に、「担当・モデルを切り替える」が標準で出ていた。技術詳細へ移した。

### ランタイムの不足（画面の不具合ではない。Codex への連絡事項）
- 架空データの承認に `attempt` が無く、`/api/decide` が 400（`'attempt'`）になる。承認の `attempt` を、対象の担当の値に合わせる必要がある（既定の 0 では「失効」になる）。
- 質問の担当が `awaiting_approval` のため、回答すると「このタスクは再試行できません。」になる。実際の流れでは、質問で止まった担当は `blocked`。
- 計画作成・計画承認の承認が、各ゲートに必要な項目（指紋・版・計画の中身）を持たず、操作できない。計画承認の画面が確認できない。
- 完了した通常レビューの担当と結果が無く、レビュー確認と正式受領の経路に進めない。

## 4. 未検証・既知の課題
