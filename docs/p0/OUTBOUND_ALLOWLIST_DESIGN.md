# 隔離ランタイムのローカルAPI許可リスト設計案

状態：設計案。ガードの動作変更・実装・テスト追加は未実施。

## 目的と判断

隔離したP0/E1の確認で、同じローカルHTTP確認のたびに自由形式のコマンドを個別承認する手間を減らす。一方、`127.0.0.1` をコマンドに書くだけで任意の通信を自動許可する穴は作らない。

- `team_outbound_guard.classify(command)` に、文字列からloopback例外を推測する規則は追加しない。
- Bash、curl、urllib等の自由形式ネットワーク操作は、loopback宛てでも現在どおり個別承認する。
- 承認を減らす経路を作るなら、任意コマンドの解析ではなく、采来が提供する専用の構造化「ローカル確認操作」に限定する。

## 操作契約

モデルにはURL、host、port、HTTP method、任意pathを指定させず、サーバー定義済み操作IDと型付き引数だけを渡す。

```json
{
  "operation_id": "p0_product_lookup_get",
  "arguments": { "product_id": "P0001" }
}
```

隔離ランタイムが、job・task・起動中プロセスにひもづいた一時許可記録を発行する。Provider入力から許可記録を作ることはできず、サーバー内で保持する。operation IDからサーバーがmethodとpathを決定し、プロセスに割り当てたloopback portにだけ要求する。

例：`p0_product_lookup_get` は `GET /?id=<検証済みproduct_id>` に固定する。`product_id` は空欄、書式不正、範囲内ID、未登録IDの試験ケースだけを許可する。host/portは引数に含めず、path traversal、任意query、任意header/bodyは受け付けない。

操作開始前に、対象プロセス、method/path、許可する入力集合、最大要求数、有効期限をまとめた確認範囲を一度表示する。利用者がその範囲を確認した後は、同じjob/runtime内の列挙済み操作を繰り返し承認なしで実行できる。範囲外の操作は自動で許可せず、別途確認へ回す。既存のG2/G3で明示的に承認された受入条件に完全に一致する場合は、その承認記録を確認範囲の根拠として再利用できるかを実装時に検討する。

## 必須の境界

- 許可記録は一時runtime ID・job ID・task ID・実行プロセスID・割当port・有効期限に束縛し、runtime終了時に破棄する。
- 接続先は `127.0.0.1` と、その実行で割り当てた単一portに固定する。ホスト名解決、環境proxy、任意redirectを使わない。redirect応答は追跡せず失敗として返す。
- method/path/queryはサーバー内の静的な操作定義から作る。未知の操作・引数・pathは拒否し、自動実行へフォールバックしない。
- 操作回数・応答サイズ・timeoutに上限を設ける。返却本文は既存の出力ガードを通し、秘密・個人情報等の保護を維持する。
- 承認画面は構造化データから、操作名・対象job内プロセス・method/path・入力集合・最大回数・期限を表示する。GETというmethodだけを根拠に「副作用なし」と表示しない。アプリ側の副作用は別途確認が必要。
- 書き込み操作、認証情報、別プロジェクト、通常サービス（8790等）、Provider通信、任意loopback portは対象外。既存の利用者承認・G2/G3・完了承認を迂回しない。
- 起動したアプリプロセス自身の外向き通信制御は別の境界であり、この許可リストは緩和しない。プロセスの外部通信は既存のガード／実行環境ポリシーを維持する。

## 方式の比較

| 方式 | 効果 | 残る問題 | 判断 |
|---|---|---|---|
| コマンド文字列のloopback例外 | 実装が小さい | 接続先をファイル・設定・環境変数から読む、redirectやproxyを使う等を静的解析で見抜けない | 不採用。`30cf6c9` の再現で確認済み |
| サーバー実装の構造化操作API | 任意URLをモデルに渡さず、method/pathと引数をサーバー側で制限できる | 対象プロセスとportの束縛、入力・応答の制限が必要 | 隔離runtime向けの次候補 |
| OS/コンテナの通信分離 | プロセスから到達できるネットワーク自体を制限できる | Windows環境への導入・配布・運用の作業が大きい | 将来の多層防御 |
| 全loopback通信を個別承認 | すぐ維持でき、未知の通信を許可しない | 確認が繰り返し発生する | 構造化操作が実装されるまでの現行動作 |

## 実装前の受入条件

1. 既知の操作ID・有効な型付き引数だけが割当portへ接続できる。
2. 任意URL、別port、別job/task/runtime、期限切れ許可、未知操作、path traversal、余分なquery/body、redirectは拒否される。
3. proxy環境変数やDNS設定を置いても接続先を変更できない。
4. `urlopen('http://127.0.0.1/'); urlopen(read_target_from_file())`、設定JSONの宛先、`curl -L` 等を使う自由形式コマンドは従来どおり個別承認になる。
5. 完全に隔離した一時runtimeで、操作の表示・実行・終了後の許可失効を確認する。通常サービス、DB、Provider通信には接続しない。
6. 承認画面は構造化操作の内容を正確に表示し、利用者の既存承認や完了承認を代行しない。

実装はこれらの境界を確認できる隔離環境を用意してから着手する。一般の通信ガードを緩める変更は含めない。
