# モデル間の引き継ぎDB

## 狙いと適用範囲

`HANDOFF.md` の記述と直近の担当結果だけでは、過去の質問への回答が欠ける。担当を新規のCodex/Claude Code CLIで起動するたびに、統括サービスが `data/handoff.sqlite3` を照会して必要な文脈を渡す。現依頼の記録を優先し、同一プロジェクトの前の依頼で利用者が答えた項目も出典付きの参考情報として渡す。他のプロジェクトの情報は渡さない。既存の `HANDOFF.md` は最新版と過去版をDBに取り込む参考資料で、判断の正本は利用者の回答と確認済みの現在情報とする。

## 記録する内容

- 元の依頼、担当ごとの指示と構造化結果、質問と選択した回答、計画・成果に対する判断を出典・日時付きで保存する。操作承認のコマンド本体とプロバイダの生ログは引き継ぎDBへ複製しない。
- `HANDOFF.md` は内容と更新時刻で版を識別し、変更の履歴を残す。
- 担当モデルは結果の `context_updates` に新しい事実・根拠を最大20件まで記す。統括が `model_reported` として保存する。AIの報告は検証済み事実とは表示しない。
- 質問への利用者の回答は `user_decision` として現在情報へ反映する。同じ項目の異なる値が出た場合は従来値を維持し、差分を矛盾として記録する。
- 新旧の矛盾があると、次の担当を停止し、タスクカードに「従来」「新しい報告」「正しい内容を入力」の選択肢を出す。利用者が回答した版を現在情報として採用し、両版と判断履歴を保持する。

## 読み出し

担当開始前にDBを更新・照会する。プロンプトには、現在情報、利用者の判断履歴、各担当の最新指示・結果、プロジェクトの最新版 `HANDOFF.md` を出典付きで渡す。過去版はDBとダッシュボードに残す。最大文脈長を超えたときに末尾だけを黙って切り取らず、担当を停止して整理が必要と報告する。モデルには質問前に渡されたDB文脈を確認し、不足分はプロジェクトを調べて `context_updates` へ返すよう指示する。

タスクカードの「引き継ぎDB」で現在情報、担当間のやり取り、`HANDOFF.md` の版履歴を確認できる。履歴は50件ずつ追加表示する。既存のDBにある依頼・結果・回答は初回起動時に取り込む。既存の依頼を再開したり、ゲームの仕様判断を変更したりはしない。

利用者はタスク詳細の「引き継ぎ情報を登録・訂正する」から、項目・現在の内容・根拠を直接保存できる。現在の依頼では利用者が登録した版を優先する。未解決の矛盾がある項目は、この欄で上書きせず判断欄で解決する。

## プライバシーと復旧

DBはこのPCの `data` 内だけに保存し、スマホ画面も認証済みの同一プロジェクト依頼からのみ読む。作業情報は担当AIのサービスへ送信される。秘密情報は `context_updates` に書かせず、秘密を示すキー名のモデル報告は現在情報へ取り込まない。モデル結果や元の依頼自体の秘密を完全自動で検出できるわけではないため、登録時の送信可能範囲は従来どおり利用者が指定する。

画面のバックアップ操作は `team.sqlite3` と `handoff.sqlite3` を対で保存する。復元時も対で扱う。実装を戻す場合は正常停止し、`data/backups/handoff-db-20260928/` の変更前ソースを元の位置へ戻す。引き継ぎDBは削除せず退避する。既存のタスクDBとプロジェクトの編集内容は自動では巻き戻さない。

## 未確認

実際のCodex→Claude→Codexの往復で `context_updates` の記録と質問抑制を確認する必要がある。矛盾の判断画面も実案件では未確認。画面に表示した現在情報・履歴の読み出しと、既存DBからの取り込みは確認済み。
