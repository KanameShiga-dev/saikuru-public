## 設計

- 人 → ダッシュボード → 統括サービス → プロバイダ接続部 → Codex / Claude Code
- タスクの状態・依存関係・承認・停止・再試行は統括サービスが管理します。
- 担当交代時は引き継ぎDBから最新情報、利用者の回答、担当結果を読み、矛盾する情報は利用者の判断を待ちます。
- 計画・実装・レビューという役割とモデル名を分離し、実行時の設定を保存します。
- 初期設定は計画/レビューをCodex、実装をClaude Codeに割り当てます。能力の優劣を断定した固定設計ではありません。
- モデル変更は新しいプロファイルとして保存し、新規作成タスクから適用します。作成済みタスクの設定は保持します。変更先のモデル適合試験は本格利用前に別途必要です。
- 同じプロジェクトの作業は直列化し、再起動後の実行中タスクは中断扱いで停止します。
- 承認待ちは操作内容と実行IDに結び付けます。拒否・取消・期限切れは実行許可になりません。
- PC画面のHTTPサーバーはループバック限定。自宅Wi-Fi用の認証付きHTTPS入口とは分け、ブラウザとワーカーの権限も分離します。
- 認証情報は保存・複製せず各CLIの認証を使います。タスクの指示・必要な作業内容は各AIのサービスに送信されます。
- 同じWindowsユーザーで動くため、悪意あるローカルプロセスに対する強制的な隔離ではありません。
- 常駐登録、既存プロジェクトの移動、グローバル方針の置換はこのアプリの作成に含みません。

## 共通Agentとの連動

共通Agent・Skillの正本、階層配置と必要時読み込みへの移行は [共通ハーネス導入記録](docs/SHARED_HARNESS_20260930.md) を参照してください。新規コンバートではAGENTS.md/CLAUDE.mdを短いrouterとして生成します。既存ファイルは通常のプレビュー・競合確認を経て扱います。

2026-09-30のCodex実行環境復旧と実CLIの検証結果は [復旧記録](docs/SANDBOX_RECOVERY_20260930.md) を参照してください。

CLI開始前にClaudeのログイン状態とCodexのWindowsサンドボックスを確認します。失敗時はモデルのターンを開始せず停止理由を表示します。Claudeの再ログインにはCLIの `auth login` を使用します。Computer Useが基本禁止の設定ならCodex担当の起動でも機能を無効にします。ClaudeのJSON結果フォーマッタ `StructuredOutput` だけは共通Agentの読み取り・編集ツールに加えて許可します。このツールはファイル・シェル操作を実行しません。

タスク実行時にユーザー領域の共通Agent定義を読み込み、Agent Teamが担当ごとに独立したCLIセッションを直接起動します。計画・調査は `common-explorer`、実装は `common-implementer`、通常レビューは `common-reviewer` を使用します。計画担当が認証・権限・秘密情報・外部送信・破壊操作などに関わる変更と判断した場合は、通常レビューの後に `common-security-reviewer` の独立タスクを追加します。専用レビューは追加のCLI利用枠を消費します。修正が必要なら実装と両レビューを再作成し、必須レビューが完了するまで成果受入へ進みません。

Codexタスクは `%USERPROFILE%\.codex\agents\<name>.toml` を解析し、`thread/start` の `developerInstructions` と `sandbox` へ適用します。導入済みCodex APIにはAgent名指定の起動RPCがないため、Agent Teamが共通定義を専用threadのネイティブ設定へ変換します。これはモデルの `spawn_agent` による子Agentではありません。Claude Codeは `%USERPROFILE%\.claude\agents\<name>.md` を解析し、安全なprompt/tools/descriptionだけを一時的な `--agents` ファイルに渡して `--agent <name>` でセッション全体の担当を指定します。プロジェクト内の同名定義やMCP・hooks設定は採用しません。モデル・推論強度はAgent Teamで選んだプロファイルが優先されます。

定義は開始ごとに再読込し、欠落・形式不正・権限拡大は明示的な失敗とします。画面に担当Agent、起動方式、実セッションID、状態、定義ハッシュを表示し、再試行の前回記録を最大30件保持します。過去タスクに起動記録を捏造しません。結果・進捗・承認・中止・再試行は既存のボードへ接続します。各担当からの追加子Agent起動は無効にし、統括が必要な担当だけを順番に起動します。Claudeの一時Agentファイルは実行終了時に削除し、タスク本文や認証情報を含めません。

## 通信切断後の手動再開

P0開発依頼で、AIサービスのDNS解決失敗・接続リセットなどが記録された場合は「通信回復後の再開待ち」と表示します。無線LANなどの接続を戻し、停止した担当の詳細で「接続と停止状態を確認」を押してください。保存済み成果と表示された操作結果を確認してチェックを入れ、「停止した担当から再開」を押すと、同じ担当・モデルで未完了部分を続けます。自動再実行・モデル切替・完了扱いはしません。

接続確認は固定のAIサービス接続先へのDNS・TLS疎通だけで、認証情報・依頼・ソースは送らず、モデルも呼びません。確認は最大8秒で打ち切り、再開時にも接続と対象の状態版を確認します。疎通成功はCLIのログイン・プロキシ経路・モデル応答の成功を保証しません。

成果・計画承認・検証証跡・停止前の操作記録は保持します。CLIの会話を復元するのではなく、停止した担当の新しい試行へ保存済み操作結果を渡します。成否不明・時間切れの操作、未処理の質問、安全上の停止、必要な保守確認やチェックポイント照合は解除しません。計画担当の再開には従来どおり新しいAI開始承認が必要です。既存のDNS失敗も起動時に表示を整理しますが、依頼は自動で再開しません。

## 運用上の境界と未確認事項

正式受領で止まった場合は、受領ボタン直下に拒否理由を表示します。「受領できない理由を確認」は正式受領と同じ検査だけを行い、依頼や承認を受領済みに変更しません。通信・応答待ちが時間切れになった場合も結果未確認のエラーを表示し、同じ受領操作を自動で再送しません。

Web成果は「ページを開く準備」から起動できます。プロジェクト内の既存の起動・停止スクリプトと空きポートを采来が選び、起動・停止を個別に許可した後でページを別タブに開きます。ポップアップがブロックされた場合は「反映済みのWebページを開く」リンクを使ってください。設定が一意に決まらない場合だけ詳細設定を使います。起動は画面の合格・正式受領とは別です。

条件別レビューの「利用者確認待ち」は、受入条件の原文を `pending_checks` に残し、`pending_check_details.source_excerpt` に同じ承認済み条件の全文を引用して対応付けます。`check` は具体的な画面確認手順でも構いません。説明文と条件文の違いだけで実装修正へ戻しません。原文・出典・担当・必須性・実施可能性の不足や、実際の不合格は引き続き拒否します。解消済みの通信障害は現在の保守待ちとして表示しません。

旧検査だけで拒否された保存済みの最新レビューは、認証済み画面操作の `/api/recovery/recheck-criteria`（`id`、`confirmed: true`）で再検査できます。未解決の指摘・安全停止・必要な保守確認・他の実行中作業があれば拒否し、元の報告を履歴に残します。再検査はAI再生成や修正上限の解除ではなく、未完了の後続レビューまたは利用者確認へ進める操作です。正式受領は行いません。

修正で登録済み成果物が変わった場合、最終レビューでは直前の修正担当が成功させた指定検証の証跡と全登録ファイルのハッシュが一致するときだけ、成果物の版を更新します。更新前後のハッシュと検証担当は履歴に残します。検証後の変更・証跡不足では更新しません。この版の不整合だけで停止した最新の保存済みレビューは `/api/recovery/recheck-artifacts`（`id`、`confirmed: true`）で同じ照合を行えます。画面確認・正式受領や実際のレビュー指摘は省略しません。

AIの報告だけで完了とは判断しません。削除・公開・外部送信・権限変更は作業範囲と承認を確認してください。CLIへ渡した作業内容は各提供サービスへ送信されます。ローカルDB・ZIP・ログは個人情報を含み得るため公開しないでください。
